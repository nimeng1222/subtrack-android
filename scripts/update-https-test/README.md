# Isolated update HTTPS fixture (TEST ONLY)

`python3 scripts/test-update-https-fixture.py` exercises the actual loopback TLS server with synthetic bytes. It checks the host rejects an unknown CA and incorrect hostname, accepts the explicit temporary CA, checks the separately pinned manifest signature, and detects modified manifest/APK bytes. It does not install an Android application and cannot prove device or installer behavior. All host test keys and files are in a temporary directory cleaned when the test completes.

For Android integration, work only in a dedicated debug/test build and a disposable emulator:

1. `python3 scripts/update-https-fixture.py init --dir /private/tmp/subtrack-update-test-UNIQUE` creates two unrelated sets of test material: `tls-ca.pem`/`tls-server.pem` for TLS and `manifest-test-public.b64` plus its private signing key for the update manifest. The directory must not already exist. The generated private keys are mode 0600. Treat them as test material only; do not put them in any release configuration or repository.
2. Produce a same-application, higher-version Debug candidate signed with the currently installed Debug signer and a second candidate with the same package/version signed by an independently generated **test-only** signer. Keep both in a disposable directory. The fixture never signs an APK. Pass both with `serve --dir ... --apk ... --wrong-signer-apk ... --version-code ...` (defaults to 127.0.0.1:18443). Its HTTPS certificate SAN covers localhost, 127.0.0.1 and 10.0.2.2.
3. Provide the generated `tls-ca.pem` to an isolated **debug-only** network-security configuration for the fixture host, and pin the manifest public key separately. Do not add the test CA to Release or trust all certificates. `adb -s SERIAL reverse tcp:18443 tcp:18443` exposes only this server to the disposable emulator.
4. Copy `UpdateHttpsDeviceTest.kt` into the isolated Android test source, register its class in the strict `Round2Instrumentation` JUnit list, and pass `-e updateFixtureBase https://127.0.0.1:18443 -e updateFixturePublicKey BASE64` to instrumentation. The key is public and must come from the local generated file, not from the HTTPS response under test. The strict gate must still validate every result, the full summary and `INSTRUMENTATION_CODE`; an adb exit code alone is insufficient. Do not register the class in the normal test inventory until the gate provisions the fixture and passes the arguments: it intentionally fails when either argument is missing.

Endpoints: `/manifest/valid`, `/manifest/slow`, `/manifest/slow-apk`, `/manifest/bad-signature`, `/manifest/tampered-manifest`, `/manifest/tampered-apk`, `/manifest/wrong-signer`; corresponding download endpoints are selected by each signed payload. `slow` waits six seconds, supporting cancellation tests. The wrong-signer fixture must use a genuinely different certificate while preserving the candidate's package/version. Logs omit headers, payloads and private material.

The device test directly checks manifest trust, download hash, APK signer and cancellation. It does **not** test the production settings UI's disable/clear/change/leaving lifecycle, system PackageInstaller confirmation, data-preserving installation, or certificate-rotation chains; those need the host integration and actual UI/installer matrix. This fixture alone is not a production trust root or formal release proof.
